# 数据与使用说明

> 项目目录：`C:\Users\28277\Desktop\ANY\ecnomic`

## 1. 系统能做什么

系统面向商品经营异常，完成以下闭环：

```text
原始行为数据
  → 日指标聚合
  → 规则检测异常
  → 创建任务
  → Worker 调用 Agent 调查
  → 结构化诊断报告
  → 网页面板 / 可选 Webhook 告警
```

它不是实时监听每一条事件，而是按设定窗口运行检测。Scheduler 开启后可每天自动检测；Worker 常驻时会自动消费诊断任务。Webhook 未配置时只生成报告，不对外告警。

## 2. 数据与指标口径

原始数据来自 Retailrocket：

| 文件 | 内容 | 用途 |
|---|---|---|
| `events.csv` | 浏览、加购、成交行为 | 核心指标和漏斗 |
| `item_properties*.csv` | 商品属性变更 | 价格、类目、上下架 |
| `category_tree.csv` | 类目父子关系 | 类目聚合和同行比较 |

主要数据库表：

| 表 | 作用 |
|---|---|
| `raw_events` | 原始行为数据 |
| `daily_item_stat` | 按天、商品、维度聚合的指标宽表 |
| `item_price/item_category/item_availability` | 商品维表 |
| `anomaly_event` | 规则发现的商品级/类目级异常 |
| `task` | 持久化诊断任务队列 |
| `diagnostic_report` | Agent 最终报告 |
| `tool_call_log` | 工具调用审计 |

重要口径：

- 漏斗是“浏览→加购→成交”，原数据没有独立曝光、点击和支付字段。
- GMV = 成交笔数 × 商品最新价格，尚未按交易当天生效价精确关联。
- 仅价格、类目、上下架三个属性可解释，其余属性已哈希。

## 3. Agent 如何诊断

Agent 不再固定调用全部工具，而是维护“假设—证据—置信度”状态：先提出可能原因，再根据已有线索选择 `metric`、`funnel`、`peer` 或 `dimension`，观察新证据后更新判断。

报告只有通过数字一致性、证据支撑、归因、建议可执行性和叙事一致性检查后才会标记成功。不合格报告返回 `incomplete`，不会被当作成功结果，也不会触发告警。

## 4. 启动和停止

首次安装：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

启动 API 和 Worker：

```powershell
.\.venv\Scripts\python.exe scripts\manage_services.py start api
.\.venv\Scripts\python.exe scripts\manage_services.py start worker
.\.venv\Scripts\python.exe scripts\manage_services.py status
```

Scheduler 是可选的。只有希望每天自动检测时才启动：

```powershell
.\.venv\Scripts\python.exe scripts\manage_services.py start scheduler
```

也可双击 `start_all.bat` / `stop_all.bat` 一键启停全部服务。服务日志位于 `logs/service/`。

## 5. 网页面板

API 启动后打开：

`http://127.0.0.1:8000/api/v1/monitoring/dashboard`

右上角输入项目 API Key。Key 存在项目根目录 `API_KEY.txt` 或 `.env` 的 `API_KEYS` 配置中；不要把真实 Key 写入文档或提交 Git。

面板主要展示：

- 诊断次数、错误率、LLM 延迟、token 成本和任务积压；
- 商品级/类目级异常及诊断报告；
- 工具调用趋势、慢查询和用户反馈；
- Webhook 是否配置。

报告中的 `run_id` 可用于检索 `logs/agent_runs/`、`logs/tool_calls/` 和 `logs/sql_logs/`，还原完整调查过程。

## 6. 常用命令

```powershell
# 导入和检测
.\.venv\Scripts\python.exe scripts\import_retailrocket.py
.\.venv\Scripts\python.exe scripts\run_detection.py
.\.venv\Scripts\python.exe scripts\run_detection.py --no-diagnose

# 查看监控
.\.venv\Scripts\python.exe scripts\monitoring_report.py --hours 24

# 测试与评估
.\.venv\Scripts\pytest.exe -q
.\.venv\Scripts\python.exe evaluation\cases_runner.py
```

`cases_runner.py` 使用真实模型时会消耗 API token；日常回归优先运行全离线 pytest。

主要 API（均以 `/api/v1` 为前缀，除健康检查外需要 `X-API-Key`）：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/diagnostics` | 同步诊断或创建异步任务 |
| GET | `/tasks/{id}` | 查询任务状态 |
| GET | `/monitoring/anomalies` | 查询异常列表 |
| GET | `/monitoring/reports/{anomaly_id}` | 查询异常对应报告 |
| GET | `/monitoring/dashboard` | 打开监控面板 |
| POST | `/feedback` | 提交报告反馈 |
| GET | `/docs` | Swagger 文档 |

## 7. 手动验证完整流程且不发送告警

1. 保持 `.env` 中 `ALERT_WEBHOOK_URL=` 为空。
2. 启动 API 和 Worker，Scheduler 可以关闭。
3. 选择已有商品级异常，通过 `/diagnostics` 提交诊断。
4. 用 `/tasks/{id}` 确认任务成功。
5. 用 `/monitoring/reports/{anomaly_id}` 查看报告和 `run_id`。
6. 若状态为 `incomplete`，按 `run_id` 检查 Agent 与工具日志，确认是哪项质量门槛未通过。

已完成的真实样例：异常 `938` → 任务 `16` → Agent 调查分支 `metric→peer→funnel` → 报告落库并能由 API 读取。主归因为商品不可用状态造成流量下降，置信度 0.85；Webhook 为空，未发送告警。样例 ID 依赖当前本地数据库，重新建库后可能变化。

## 8. 总目录改名后的检查

Windows venv 的激活脚本和命令启动器可能保存创建时的绝对路径。目录迁移后执行：

```powershell
.\.venv\Scripts\python.exe -c "import sys; print(sys.executable); print(sys.prefix)"
.\.venv\Scripts\pytest.exe --version
.\.venv\Scripts\uvicorn.exe --version
```

输出应位于 `C:\Users\28277\Desktop\ANY\ecnomic\.venv`。如果仍指向旧目录，最稳妥的处理是在新目录重建 `.venv` 并重新安装依赖。正常的 `数据/`、中文文档名和业务字段不受总目录改名影响，不需要修改。

当前验证结果：`75 passed`；Python、pytest、uvicorn 和 pip 均从新英文目录运行。

## 9. 当前限制

- 价格使用最新价近似，尚未按日生效。
- 数据集属性大多已哈希，无法解释完整商品属性。
- 类目级异常依赖代表商品辅助调查。
- Scheduler 关闭时不会自动运行新一轮检测。
- Webhook 未配置时不会对外报警，但诊断和报告不受影响。

更多架构原因和关键踩坑见 `docs/设计说明.md`。
