# 电商经营异常诊断 Agent：设计说明

> 代码库：`C:\Users\28277\Desktop\ANY\ecnomic`

## 1. 系统目标与边界

系统自动完成“发现异常→调查原因→生成报告→展示/可选告警”。SQL/Python 规则引擎负责发现异常；Agent 根据线索选择调查路径；LLM 提出假设、更新判断并组织报告；确定性代码负责权限、预算、证据校验和质量守门；数据库保存异常、任务、报告和审计记录。

Agent 不能任意执行 SQL 或写数据库，只能调用四个白名单工具。因此它是一个**受约束的领域调查 Agent**，不是通用自治 Agent。

## 2. 总体流程

```text
Retailrocket CSV
  → 导入与日聚合 daily_item_stat
  → 规则检测 anomaly_event
  → 创建诊断任务 task
  → Worker 调用 Agent
  → 假设—取证—更新置信度—选择下一分支
  → 质量门槛
  → diagnostic_report
  → 监控面板 / 可选 Webhook 告警
```

数据层采用原始表、维表、指标宽表三层。指标定义集中在 `app/metrics/definitions.yaml`，避免检测、工具和报告使用不同口径。当前漏斗为“浏览→加购→成交”；GMV 使用成交笔数乘商品最新价，是数据集限制下的近似口径。

## 3. Agent 的核心变化

### 3.1 从固定 Workflow 到动态调查

旧实现虽然调用 LLM，但路径基本固定为 `metric→funnel→dimension`，评估也奖励工具和关键词命中，因此更接近“在 Workflow 中嵌入 LLM”。现在的循环结合 Plan-and-Execute 与 ReAct：

```text
提出可证伪假设
  → 选择当前信息增益最高的工具
  → 观察结构化证据
  → 支持、反驳或降低假设置信度
  → 继续调查、切换分支或形成结论
```

| 问题 | 工具 |
|---|---|
| 异常趋势、前后窗口、价格或上下架 | `MetricTool` |
| 损失发生在哪个转化环节 | `FunnelTool` |
| 商品自身问题还是类目整体变化 | `PeerTool` |
| 是否集中于新老用户、工作日等切片 | `DimensionTool` |

工具不需要全部调用；缺少支撑结论的证据才是失败。

### 3.2 “假设—证据—置信度”状态

`InvestigationState` 显式保存假设 ID、描述、状态、置信度、成功工具调用形成的证据、稳定的 `call_id` 与数据路径，以及最终主归因。这相当于 LangGraph 等状态图架构里的共享 State，但本项目用纯 Python 实现。关键不是使用哪个框架，而是后续决策能真正读取并更新状态。

### 3.3 证据与报告质量门槛

工具结果以紧凑结构化 JSON 回填给模型。报告中的关键数字必须通过 `call_id + data path` 指向原始工具值，避免摘要抄错和数字幻觉。

最终报告检查：

1. 数字一致性。
2. 事实和假设的证据支撑度。
3. 主归因与人工真值的一致性；未标注时显示 `needs_label`。
4. 建议是否包含动作、负责人、优先级和成功指标。
5. 结论与证据方向是否矛盾。

质量不合格时最多要求模型修正两次，仍失败则返回 `incomplete`。队列不会把这类报告误记为成功，也不会继续触发告警。

## 4. 安全、稳定性与审计

| 防线 | 作用 |
|---|---|
| `agent_ro` 只读数据库账号 | Agent 无法写库 |
| 工具白名单、参数化 SQL、日期/行数限制 | 防越权和超大查询 |
| `max_steps`、总超时、token 预算、Context 裁剪 | 防无限循环、挂死和成本失控 |
| `run_id` + DB/JSONL 日志 | 回溯模型决策、工具输入输出和耗时 |
| API Key、限流、安全响应头 | 保护外部接口 |
| Webhook 空配置默认关闭、HMAC 签名 | 避免误告警并校验消息来源 |

任务队列使用数据库实现持久化、幂等、优先级、重试和并发抢占。当前规模不需要先引入 Redis/Celery；任务量或多副本需求上升时再迁移。

## 5. 评估与验证结果

旧版“工具序列+关键词”评估曾得到 100%，但只能证明流程跑通，不能证明归因正确，现已不再作为核心质量指标。

- 全离线测试：`75 passed`。
- SQLite 覆盖 Agent、工具、队列、API、检测和面板；新 SQL 仍需在 MySQL 实数上复核方言差异。
- 历史异常 `938` 完整闭环：任务 `16`、`run_id=dd2be87edf1f45dd`。
- Agent 按线索选择 `metric→peer→funnel`，没有机械调用全部工具。
- 四项核心质量评分均为 1.0；主归因为商品不可用状态造成流量下降，置信度 0.85。
- 报告已落库并可由监控 API 查询；Webhook 为空，因此没有外发告警。

## 6. 关键踩坑

| 问题 | 处理 |
|---|---|
| 固定工具顺序形成“伪 Agent” | 改为状态驱动分支，工具无需打卡 |
| 模型引用错工具数字 | 回填结构化 JSON，以证据路径核对数字 |
| Agent 退出但报告不合格 | 显式 `complete/incomplete`，队列按质量落状态 |
| 关键词评估虚高 | 改用数字、证据、人工归因和建议四维评估 |
| 结论与证据方向矛盾 | 增加叙事一致性守门 |
| MySQL `Decimal × float` 报错 | 派生计算统一转 `float` |
| SQLite/MySQL 方言不同 | 代码兼容两端，新 SQL 必须实库验证 |
| 全量检测和导入过慢 | 批量加载后分组；导入使用 `LOAD DATA` |
| 总文件夹改名后 venv 混用旧路径 | 修正/重建 venv，验证 Python、pytest、uvicorn、pip 路径 |
| Windows 中文文档乱码 | 文档统一以 UTF-8 编辑 |

`.pyc` 中的旧源路径属于编译缓存元数据，不是运行配置。目录迁移时应检查真正会执行的激活脚本和启动器，不必机械修改缓存或历史日志。

## 7. 当前限制与后续方向

- 价格尚未按事件当日生效价关联。
- 哈希商品属性不可做业务语义解释。
- 类目级异常仍以代表商品辅助调查。
- 当前 DB 队列适合单机/低并发；多 Worker 部署可迁移 Redis/Celery。
- 数据量扩大到千万级/日后，再考虑 ClickHouse、Spark/Flink 和专业调度平台。
