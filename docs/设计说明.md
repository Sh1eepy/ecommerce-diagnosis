# 设计说明

本文解释当前设计；操作见[使用说明](数据与使用说明.md)，验收见[变更与验收](变更与验收.md)。

## 1. 各层为什么分开

| 层 | 负责什么 | 这样设计解决的问题 |
|---|---|---|
| 规则检测 | 用确定性条件发现指标异常 | 不让每次异常筛选依赖模型随机性和费用 |
| Agent Loop | 维护调查状态，选择下一步或结束 | 不再要求固定执行全部工具，避免“工具打卡” |
| LLM | 提出候选解释、选择查询、组织报告 | 使用语言推理，但不赋予它权限和执行预算的决定权 |
| 白名单工具 | 校验参数、执行预定义只读查询 | 模型不能提交任意 SQL、shell 或业务写操作 |
| Worker/队列 | 异步执行、领取、重试、恢复 | HTTP 请求不必等待长诊断，进程退出后任务仍可追踪 |
| 质量校验/持久化 | 检查事实、状态、所有权并保存结果 | “没有抛异常”不再等同于成功，迟到执行者不能随意覆盖结果 |

源码入口：[Agent](../app/agent/agent.py)、[工具注册表](../app/agent/tool.py)、[Worker](../app/tasks/worker.py)。工具只读是**模型能力边界**；服务层仍用写连接保存任务、报告和审计，不能描述成整个 Agent 进程没有写库能力。

## 2. 调查状态与工具选择

`InvestigationState` 保存候选假设、成功证据、失败调用与 `call_id`。工具返回结构化数据，模型据此继续查询或形成报告；失败工具不能进入成功证据账本。

| 工具 | 当前证据 | 不能据此确认 |
|---|---|---|
| metric | 日序列、前后窗口汇总与日记录覆盖、有条件的变化量、最新价、不可用观察点 | 无记录即无事件、整个窗口不可售、已证实因果、真实损失 |
| funnel | 浏览→加购→成交的量和比率 | 某环节变化的业务原因 |
| peer | 当前窗口类目总量、排除自身后的同行值、UV TOP 商品 | 大盘历史趋势、排除大盘影响 |
| dimension | 工作日/周末、新老用户等已有切片 | 数据源没有提供的渠道、活动或设备解释 |

无需调用全部工具，但必须有可回查事实。数据口径由导入逻辑、[计算公式](../app/metrics/registry.py)及指标配置共同决定，不能只改 YAML 就认为完成了新数据源接入。

## 3. 报告为何允许“原因未确认”

旧门槛要求 `primary_hypothesis_id` 指向 supported 假设，容易逼模型在证据不足时选一个原因。真实样例曾正常执行却生成了“大盘正常”“GMV 损失”等越界结论，说明数字和引用正确仍不够。

当前报告契约：

- `facts` 用成功证据的 `call_id + path` 引用原值，至少包含一条可核对数值。
- `facts[].section` 可选 change/focus，分别用于整体变化和环节/人群观察；不填时按旧事实展示，不强迫模型编造定位结果。
- `analysis.attribution_status = uncertain`、`primary_hypothesis_id = null`；可以不列原因假设，避免为了过关编造解释。
- 若列候选原因，保留 active/uncertain 和证据引用；现有观察工具没有独立因果验证能力，不能靠自报 confidence 或 supported/rejected 确认、排除原因。
- `limitations` 必须非空；服务端根据证据附加 `evidence_limits` 和对应说明，模型不能省略或自填“已验证”来覆盖它们。
- 建议包含非空字符串 action、rationale、owner、priority、success_metric，priority 限 P0/P1/P2，优先提出可验证的核查动作。

面板将同一份报告组织为“发生了什么→变化集中在哪里→哪些还不能确认→下一步查什么”，不再只展示结论而隐藏 limitations。缺少 focus 事实时明确尚未定位；建议按优先级展示依据、责任角色和验收条件。纯渲染函数统一新旧数据和文本转义，不在浏览器中重新推断原因。

Agent 在落盘前附加 `report_version=2`、`report_status=quality_checked/incomplete`，不采信模型自填标记；报告、返回结果与最终 checkpoint 使用同一份对象。quality_checked 只表示通过有限规则，不能解释成真实性认证。旧数据库报告和已完成 checkpoint 不重写，界面提示未按当前规则复核。

[质量检查](../app/agent/quality.py)包含数值、引用、归因边界、建议字段、叙述矛盾及已知过度断言规则。最多要求两次修正；预算允许时可补证据，持续失败则 incomplete。合格的不确定性报告可以 succeeded，**完成调查与证实根因是两回事**。

文本规则不是通用语义证明器，仍可能漏判或误拒；当前限制是保守取舍。以后若增加因果验证能力，必须定义可信证据协议与测试，不能只增加一个模型可填写的布尔值。

真实复诊暴露两种误拒后，零值叙述检查改为分句内核对主语，不跨越“但/而”、标点或不同报告字段，把成交为零误套到访客；仍拒绝“访客和成交均为零”等并列断言。因果限定词除了匹配前缀，也识别紧贴因果谓词的“库存变化可能导致”，不因同句别处出现“可能”就放行确定结论。此修复不调整证据数值、报告状态或置信度门槛，历史报告仍保留当时结果。

## 4. 状态保存与执行所有权

### 工作上下文与预算

完整工具证据留在 `InvestigationState`/checkpoint；给模型的工作上下文由 `compact_context` 重建，只保留初始任务、结构化证据、最新调查状态及当前待修正报告。中文工具摘要不再与同一份 JSON 重复发送，历史状态也不叠加。14 天以内的日序列保留；更长序列整项省略并明确告知模型不可据此描述逐日走势，不通过重排数组破坏 evidence_ref。旧 `truncate_context` 保留兼容，但主循环不再用它静默丢弃修正意见。

请求前估计输入量，并用剩余额度限制 `max_tokens`，默认单次输出不超过 2048。剩余额度不足以支持约三轮当前规模调用时，已有证据的调查进入收尾，给报告及修正留空间；模型仍要求查询则停止，不放宽报告检查。若估计输入加最小输出也放不下，不再发送请求。收到响应后按供应商实际 usage 累计，先将响应留在状态中，再检查总额度/时间，超额响应不当作成功报告。

估算不是供应商精确 tokenizer；未知失败请求用量、重试与估算误差仍可能造成实际账单超过配置。该策略减少浪费，但不承诺硬费用封顶或一定留够一次纠错。恢复沿用原累计用量，不因重新启动而扩大总预算。供应商输出参数语义见 [DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。

### 人工审查与经验

`ReportReview` 以 run_id 唯一标识被审查的版本，并保存报告内容 SHA-256、异常快照、原始反馈和审查时间。前端先打开表单，再确认写入；重复提交相同内容返回原记录，不同内容返回冲突，不覆盖旧反馈。诊断仍运行/等待恢复时不接受审查；新报告或内容摘要变化后，旧审查不会算在新版本上。异常的 open/closed 与报告的 reviewed/unreviewed 分开维护。

正确/部分正确/不正确/暂不能判断都是**人的判断**，不等于系统验证。用户输入一段反馈后可点击“自动提炼经验并预览”：LLM 接收该反馈、异常字段及至多 800 字符的原报告结论，输出可参考经验、应避免的误判、适用条件和核查依据。原报告标为未证实背景，不自动当正确答案；没有依据的经验允许为空。输入放在低信任用户消息中，无工具执行权限，模型不得补造核查记录。用户核对/修订并勾选确认后才可提交审查；是否授权后续检索仍是另一个独立选项。也可跳过模型，只保存原文或手工填写。

`ReviewDraft` 在网络调用前持久化占位，幂等键绑定报告内容摘要、Key 标识、原反馈和协议版本；相同请求无论成功、失败还是处理中，都只读取已有状态，不重新收费。同报告同 Key 最多 3 份不同反馈草稿。一次提炼最多发一个 Provider 请求，禁用其重试（不改变诊断的重试配置），默认 30 秒、6000 总 token 估计预算、1200 输出上限。失败/输出不合格/预算不足均可回到手工流程。进程中断后可能停在 generating，系统不猜测是否计费并重放；这不是自动任务恢复。最终草稿使用量纳入成本接口，未知失败费用仍不在已知 usage 内。

确认时再次核对草稿归属、报告摘要、原反馈与 ready 状态，并允许用户修订经验。草稿本身不进入检索；只有已提交且授权的审查才参与。Markdown 同时保留反馈原话、经验来源草稿 ID 和适用条件，数据库保存原模型草稿、最终人工版本及用量，避免悄悄覆盖原话。数据库为主记录，`knowledge/reviews/review-<id>.md` 为不可覆盖的阅读副本；导出失败明确提示，不能将写文件成功与事务提交混为一谈。

默认不检索人工经验；仅在用户授权后，按相同指标、规则与商品/类目层级匹配，检查来源仍是最新报告且内容未变，从最近 30 条候选中选至多 3 条、合计不超过 2400 字符。上下文标明来源与历史观察值；经验不能充当当前事实引用，当前工具仍需重新取证。报告/checkpoint 保存实际检索的 review_id/source_run_id，恢复沿用启动时快照。停用会保留反馈与停用记录，仅影响新诊断，不撤回已发出的模型请求。

文件不作为可执行指令，也不扫描任意 MD 进入系统提示。直接编辑副本不会改变数据库经验。当前没有向量检索、自动纠错训练、跨租户隔离或经验语义可信性认证；提示词与现有规则不能保证抵御所有语义注入，外部多人接入前仍需隔离与安全评估。

Checkpoint 保存完整步骤后的 messages、证据、工具历史、下一步、累计已知 token、尝试数和原始预算。只保存最新状态，不是历史回滚系统。恢复前校验任务目标和格式；缺失/损坏存档不能静默当作新任务。

Worker 按空闲槽位领取，每次领取生成凭证并续租。报告、checkpoint、任务状态写入前先在事务中检查并锁定 Task，阻止旧执行者迟到覆盖。模型/工具调用前的检查无法撤销已经发出的外部请求。

详细状态表、次数语义与崩溃窗口只在[Worker 文档](Worker运行与恢复说明.md)维护。报告事务与最终 checkpoint 不是一个原子提交，告警也没有 outbox；不能宣称整个过程 exactly-once。

## 5. 安全与可观测性取舍

| 设计 | 理由及边界 |
|---|---|
| 读写连接分开 | 工具默认走只读账号；真实账号授权仍需核对，配置中的不同用户名不等于权限已正确设置 |
| API scope + 输入边界 | 将读报告、创建诊断、导入、反馈分权；没有店铺/租户隔离，限流仍在进程内 |
| CSV 有界读取、逐行检查、整批事务 | 拒绝异常值及部分导入；仍是追加写入，没有重复批次幂等 |
| 反馈服务端生成文件名、前端不持久保存 Key | 降低路径注入、并发覆盖和持久泄漏风险；不能防止页面已执行的恶意脚本 |
| Provider 分类重试、Agent 预算 | 防重试叠加和无限循环；并非严格墙钟取消或费用封顶 |
| run_id 贯穿 DB 与 JSONL | 对照任务、模型、工具、SQL 和反馈；日志仍须限制访问并脱敏分享 |
| FastAPI lifespan、SQL 日期显式绑定 | 避免继续依赖弃用启动接口与 SQLite 默认日期适配器 |

`TOOL_RESULT_MAX_*` 配置不能当成所有查询都已有统一硬限制；全量结果大小、SQL 硬超时和跨进程限流仍是生产化待办。面板仍依赖 CDN/内联脚本；初始化 SQL 也不等于最小权限生产方案。

## 6. 三类验证各自证明什么

| 验证 | 能验证 | 不能替代 |
|---|---|---|
| pytest + 临时 SQLite/Mock | 状态机、错误分类、预算、确定性报告规则；部分用真实 SDK 配合模拟 HTTP 故障 | 真实模型推理质量、MySQL 锁与网络行为 |
| 隔离 MySQL 集成测试 | 事务、并发领取、租约接管、迁移和备份恢复 | 业务归因正确性 |
| 真实 LLM + 人工评估样例 | 工具选择、边界表达、报告可用性和调用成本 | 稳定覆盖罕见故障 |

[evaluation/cases_runner.py](../evaluation/cases_runner.py)会按当前应用配置执行 Agent、写运行结果，可能调用真实模型或发送配置的告警，不是 pytest 的隔离入口。其归因评分仍使用人工标签词项匹配，缺标签标为 needs_label；尚未针对“合理保留不确定性”建立完整评测，不能将评分当作语义正确性的证明。

## 7. MCP 是工具适配层，不是新 Agent

当前定位是可选协议实验，不是主业务链路或上线必需项；不为学习协议而引入额外进程通信。工具的业务通用性仍取决于数据模型、指标口径和契约，MCP 只统一接入方式。

新增 stdio MCP Server 复用同一份工具 Schema、注册表与查询；原 Agent 仍直连注册表。选择官方 SDK 低层接口是为了直接公布已有 Schema，避免重复维护装饰器参数。默认关闭，独立 tools:read 授权，不继承旧 API_KEYS；仅显式导出四个工具。

MCP 返回独立 run_id/call_id、结构化数据及服务端 evidence_limits，失败不暴露原始异常；检查输出契约与大小，限制调用频率和在途数量。超时/取消后槽位保留到真实执行结束，不伪装成 SQL 已被终止。只写本地日志，不产生诊断任务或报告，现有 DB 监控也不统计这些调用。实现、演示和真实接入边界见[MCP 学习说明](MCP接入与学习说明.md)。

## 8. 公共逻辑整理

| 原来容易重复的流程 | 统一入口与理由 |
|---|---|
| 四个工具分别解析商品与日期 | `_common.parse_item_window`；输入 Schema 与执行前业务校验仍分别保留 |
| 日序列和两期汇总分别查询 | `compute._daily_totals/item_comparison` 一次取双窗口，序列、汇总和覆盖从同批行计算；`item_summary` 保留兼容入口 |
| 每个聚合手写 SUM 列、每个比例写除法 | `_sum_columns` 与 `registry.RATIO_COMPONENTS`；固定列参数化查询，分子/分母/比例因子只有一处定义 |
| 工具、查询、CSV 各写维度白名单 | registry 的 Literal 枚举供三处使用；导入允许 all，拆解工具仍不允许 all |
| peer 为各项结果重复读类目/自身 | 每份原始汇总只读取一次，再计算派生值；保留既有 category 切片减自身口径，没有增加历史对比 |
| 商品/类目重复跑规则并记录异常 | `detector._detect_group`；查询口径仍分开，事务提交和后续入队时机不变 |
| 监控初始化多份相同桶结构 | `_empty_bucket`，避免后续新增累计字段时漏改一处 |
| Mock 从中文摘要提取数值 | 直接解析结构化证据；缺失时拒绝生成数值，不把展示文案当数据协议 |

`metrics/windows.py` 只做日期、覆盖和变化计算，不连接数据库。当前窗口日期差上限仍为 90 天，上一窗口相邻且等长，不自动按周几、节假日或活动对齐。双窗口任一方缺记录时 changes 为 null；零基线不能算相对百分比，比例分母为零时变化不可解释。旧汇总中的零值仍保留兼容，但不能忽略 coverage/changes.status 把无记录理解为真实零活动。

本轮静态检查覆盖 app/scripts/evaluation 的 Python 源码及 web 页面，人工核对相似流程；不能据此宣称所有重复都已消除。Worker 写入前的多处所有权检查保护不同事务时点，保留；监控不同平均值算法的统计含义不同，保留；检测器原始序列读取与指标工具日汇总也不强行合并。日内求和不是重复批次去重，导入幂等仍是独立待办。

### 字段不同、流程相同的三个例子

1. **商品与类目检测**：共同执行“算指标→跑规则→幂等记录→收集异常”，差异仅由各自的原始数据与 `item_id/category_id` 传入 `_detect_group`。查询来源、事务提交及入队仍由外层控制。
2. **不同指标公式**：CVR、加购率和客单价分别使用不同分子、分母和倍率，`RATIO_COMPONENTS` 描述这些差异，`compute_metrics` 统一类型转换、零分母处理和舍入；基础指标仍直接透传。
3. **当前与上一窗口**：日期边界不同，但筛选日记录、求和、计算指标和覆盖的流程相同，由 `compare_windows` 循环执行；两期的对比条件在同一处判断，避免漏改其中一期。

这是把业务差异作为参数或配置，把相同处理过程保留为一份实现。四工具参数解析和监控空桶则属于普通的相同代码重复；两类重构都已完成，不只是改了字段名称。
