# 生产化问题与设计对照

当前定位：**有人复核的诊断原型，尚非可无人值守的生产业务 Agent**。已完成什么见[变更与验收](变更与验收.md)，设计理由见[设计说明](设计说明.md)。

## 1. 已有防线不等于完整保证

| 已具备 | 仍需区分 |
|---|---|
| 白名单读取工具、参数校验、读写连接分离 | 模型不能任意写业务数据，但服务进程持有写连接；真实授权需核查 |
| API scope、限流、上传边界、反馈校验、安全响应头 | scope 不是租户隔离，限流不是跨进程，全站安全不能只靠响应头 |
| 队列幂等、checkpoint、租约/心跳、fencing、预算恢复 | 正常路径实测通过，MySQL 并发与故障演练仍缺 |
| 数字/引用检查、不确定性协议、服务端证据限制 | 有限规则会漏判或误拒；不能当成因果证明或诊断准确率 |
| 双窗口记录覆盖、四段运营报告、旧报告未复核提示 | 日记录齐全不证明数据质量；仍需真实模型和人工核查报告可用性，页面可视布局验收待做 |
| 请求前预算估计、输出限制、上下文去重与低预算收尾 | 已取得模型响应的复诊及补跑均在当前额度内结束，但不都得到合格报告，不是账单硬封顶或性能基准 |
| LLM 反馈提炼草稿、人工确认、版本审查、经验授权、Markdown 副本及检索停用 | 代码与接口检查完成；真实反馈提炼仍需人工验收，模型总结与人的判断不自动变成事实，未实现跨租户隔离或语义注入完整防护 |
| 四个工具的 stdio MCP 适配、显式 tools:read、结构化错误和证据限制 | 隔离测试通过；未接通真实客户端，无远程 OAuth/租户隔离，MCP 调用只记本地日志 |
| run_id 日志、监控、用量估算、Webhook | 成本不是完整账单，告警没有可靠 outbox |
| 本地离线回归、CI 配置、扫描入口 | 本机测试通过不代表远端 CI、依赖漏洞和密钥扫描已通过 |

## 2. 优先补齐的缺口

| 优先级 | 问题及影响 | 下一步与验收标准 |
|---|---|---|
| P0 | 真实报告质量仍不稳定 | 真实样例中存在反复错引数字，以及把“有加购无成交”说成“问题集中在支付环节”的情况，说明数值修正和语义门槛仍不稳定。先优化事实与文字绑定、定位证据边界、重复修正停止及准确失败说明，再经授权复测，不直接放宽门槛 |
| P0 | 无备份恢复与真实故障验收 | 在隔离 MySQL 恢复备份；测试双 Worker 抢占、进程退出、租约接管、断连和预算耗尽，确认不越权写入 |
| P0 | 用户/店铺数据未隔离 | 多用户接入前补身份、数据归属、查询过滤和反向越权测试；完成前限定受信任内部使用 |
| P0 | 初始化账号权限偏大 | create_users.sql 实际包含 DROP 与 '%' 来源；区分迁移账号和运行账号，核查 SHOW GRANTS，再经批准收紧 |
| P1 | 业务口径会误导归因 | 核实属性价格与货币单位，补历史生效价、窗口去重 UV、数据完整性，形成可核对样例；按当前范围保留 peer 单窗口边界，不增加同行历史对比 |
| P1 | 导入和未来写工具无完整幂等 | CSV 重复导入会重复计数；设计批次键、冲突策略。写工具另需审批、幂等和补偿，不直接套只读恢复逻辑 |
| P1 | 告警可能漏发，边界信息不完整 | 设计事务 outbox、受控重试和接收方去重；当前 payload 未结构化携带 attribution_status/limitations，接入业务群前补齐与验证 |
| P1 | 成本、资源和页面防护不完整 | 旧实现的真实调用曾超出 30,000 tokens；优化后的复诊及补跑未超额度，但仍需更多样例、未知失败费用核对和修正重复检测。另补查询/响应大小限制、跨实例限流、CDN/内联脚本与日志防护 |
| P1 | 评估与部署可复现性不足 | 标注可接受的不确定性；修正词项匹配评分的局限；锁定依赖并验证 CI，建立服务拉起和优雅停止流程 |
| 可选实验 | MCP 已完成适配学习目标，不是当前上线阻塞项 | 默认关闭，原 Agent 直调工具；仅在出现外部复用需求后，再评估宿主接入、授权和部署边界 |

这些是待办，不是本次文档修改已完成的能力。改变真实账号、数据、服务或外发行为前仍需确认范围。

## 3. 推荐执行顺序

1. 先验收新报告协议：已核对的事实、待验证原因、证据限制分开，人工判断是否真正有用。
2. 再做隔离 MySQL 故障与备份恢复：把“代码支持恢复”变成“在目标环境验证过恢复”。
3. 明确实际用户和业务范围：多人/多店铺场景先补数据隔离，外部写操作先补审批与幂等。
4. MCP 适配实验已收尾，不继续扩大为客户端改造或远程服务；优先解决以上业务与可靠性缺口。是否换队列或分析数据库，由积压、锁等待、故障率和查询延迟决定。

当前 DB 队列已经有并发领取逻辑；无需为了“多 Worker”就必然更换 Redis/Celery。扩大部署之前先测清现有实现的正确性和瓶颈。

## 4. 值得亲手学习的部分

| 学习点 | 建议的小实验 | 必须保留的边界 |
|---|---|---|
| Worker 恢复 | 在隔离库让进程在完整步骤后退出，观察新执行者接管与旧凭证被拒 | 不强杀真实业务任务，不靠重置预算实现恢复 |
| 不确定性评估 | 为同一份证据写“合理保留未知”和“过度归因”两个报告，解释为什么应分别接受/拒绝 | Mock 验证规则，真实模型验证表现，两者都要有 |
| MCP 工具适配 | 先运行已提供的进程内演示，再跟踪一个调用经过 schema、鉴权、执行、结果封装的过程，见 [MCP 说明](MCP接入与学习说明.md) | MCP 是接口协议，不自动提供租户隔离、安全查询或可靠重试 |
| 副作用管理 | 用假库存服务演练同一请求重试、重复提交、审批与补偿 | 未定义幂等契约前不接真实库存/订单 |

学习重点是契约、失败边界和验证方法，而不是重复手写条件与样板代码。
