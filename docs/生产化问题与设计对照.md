# 生产化问题与设计对照

本文只记录上线相关的主要防线、剩余缺口和演进条件。Agent 细节见 `docs/设计说明.md`。

## 1. 已具备的主要防线

| 领域 | 已实现 |
|---|---|
| 稳定性 | DB 持久化任务、幂等键、优先级、指数退避、并发抢占、卡死任务回收 |
| Agent 质量 | 假设驱动分支、结构化证据、数字/证据/归因/建议/叙事质量门槛、`incomplete` 状态 |
| 数据准确性 | 指标注册表统一口径、原始数据保留、工具结果可追溯、真实 MySQL 复核 |
| 安全 | 工具白名单、参数化 SQL、只读账号、API Key、限流、安全响应头、密钥扫描 |
| 性能与成本 | 指标宽表、批量检测、`LOAD DATA`、步骤/超时/token 上限、慢查询与成本监控 |
| 可观测性 | `run_id` 贯穿 Agent、工具和 SQL 日志；面板展示趋势、任务、错误和反馈 |
| 告警 | Webhook 默认关闭，配置后使用 HMAC 签名；诊断失败不影响主服务 |

工程取舍：规则引擎负责可复现的异常检测，Agent 只负责调查；当前任务量使用 DB 队列即可，不提前引入 Redis/Kafka；离线测试使用 SQLite + MockLLM，新增 SQL 仍要在 MySQL 实数上验证。

## 2. 已知限制

| 缺口 | 影响 | 建议 |
|---|---|---|
| 商品价格使用最新价 | 历史 GMV 可能有近似误差 | 改为按事件日期关联生效价 |
| 单机 MySQL | 数据库故障会中断服务 | 上线前做恢复演练，正式环境使用云 RDS/主从 |
| 服务进程依赖本机脚本 | 重启或断电后可能需要人工拉起 | 使用 Windows 服务、NSSM 或容器编排 |
| DB 队列面向低并发 | 多 Worker/高吞吐能力有限 | 达到积压阈值后迁移 Redis/Celery |
| SQLite 与 MySQL 存在方言差异 | 离线测试不能覆盖全部实库问题 | 保留 MySQL 集成测试和上线前冒烟 |
| 属性大多已哈希 | 归因维度受数据源限制 | 接入业务可解释的商品、渠道和活动维度 |

## 3. 上线前最低检查

1. 在空库完成一次备份恢复演练。
2. 用真实 MySQL 和真实 LLM 跑一组有人工作出归因标签的评估集。
3. 验证 API Key、只读账号、限流和 Webhook 签名。
4. 验证 Worker 异常退出后的自动拉起和卡死任务回收。
5. 确认监控能看到任务积压、LLM 错误率、慢 SQL 和 token 成本。
6. 告警先指向测试群，确认 `incomplete` 报告不会外发后再切正式地址。

## 4. 何时升级架构

- 队列持续积压或需要多机 Worker：迁移 Redis/Celery。
- 日增数据达到千万级、MySQL 聚合成为瓶颈：迁移 ClickHouse/Doris。
- 上游改为实时事件流：引入 Kafka + Flink/Spark。
- 多团队正式运营：补 Prometheus/Grafana、集中日志、密钥托管和发布流水线。

升级依据应是监控到的瓶颈，而不是为了使用某个技术栈提前复杂化系统。
