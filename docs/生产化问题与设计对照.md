# 生产化问题与设计对照 —— 真实业务上线会遇到什么

> 用途：对照本系统的设计，梳理"真正跑业务时常见的坑"哪些已被解决、哪些是缺口。
> 结论：**设计解决了一大半常见问题（尤其安全纵深、幂等体系、可追溯），但有 4 个真实缺口需要补**（见第 2 节）。

---

## 1. 常见业务问题 × 设计防线对照

### 1.1 稳定类（最容易翻车）

| 常见问题 | 我们的防线 | 状态 |
|---|---|---|
| 重复执行（调度器跑两次/用户点两次） | 三层幂等：检测幂等、`idempotency_key` 任务幂等、诊断懒加载 | ✅ 已解决 |
| 任务失败（LLM 超时/网络抖动） | 指数退避重试（5s→10s→20s）+ `failed` 状态可查 | ✅ 已解决 |
| 多 Worker 抢同一任务 | `SELECT ... FOR UPDATE SKIP LOCKED` 抢占，任务只消费一次 | ✅ 已解决 |
| 服务重启丢数据 | 任务存 DB（持久化队列），非内存队列 | ✅ 已解决 |
| **Worker 崩溃后任务卡死** | 无超时回收——任务停在 `running` 无人接管 | ⚠️ **缺口** |
| 单机 MySQL 挂了 | 有备份脚本，但无自动化恢复演练 | ⚠️ 半解决 |

### 1.2 数据准确类（业务方最在意）

| 常见问题 | 我们的防线 | 状态 |
|---|---|---|
| 指标口径打架 | 指标注册表 `definitions.yaml` 唯一来源 | ✅ 已解决（很值钱的设计） |
| 数据错被质疑 | 保留 `raw_events` 原始层 + run_id 三件套逐条核对 | ✅ 已解决 |
| 时间/时区混乱 | 库内统一 UTC 存储 | ✅ 已解决（sql_logs 文件为本地时间，坑已记录） |
| 价格不准 | GMV=成交笔数×最新价 | ⚠️ 已知近似，未按当日价（README 已标注） |
| 脏数据进库 | 参数强校验 + LOAD DATA 基础清洗 | ⚠️ 无完整 schema 校验 |

### 1.3 安全类（LLM 项目最容易出事故）

| 常见问题 | 我们的防线 | 状态 |
|---|---|---|
| 提示注入（LLM 被诱导干坏事） | 工具白名单 → 参数强校验 → **只读 DB 账号** 三层纵深 | ✅ 解决得很彻底 |
| 密钥泄漏到 git | gitleaks 钩子 + .gitignore + 密码轮换 + git-filter-repo 洗历史 | ✅ 解决得很彻底 |
| 恶意请求刷接口 | API Key + 每分钟限流 + 文件类型/大小校验 + 安全响应头 | ✅ 已解决 |
| 面板未授权访问 | 数据接口全部要求 Key | ⚠️ 页面壳本身无鉴权（数据出不来） |

### 1.4 性能/成本类（线上被投诉的两大来源）

| 常见问题 | 我们的防线 | 状态 |
|---|---|---|
| 查询慢 | 宽表预聚合（681 万行秒级查询）+ 索引 + 慢查询 TopN 监控 | ✅ 已解决 |
| 检测慢 | 批量加载替代逐商品查库（5 分钟→秒级） | ✅ 已解决 |
| LLM 变慢/限流 | 单请求超时 + 429/5xx 指数退避 | ✅ 已解决 |
| 成本失控 | `max_steps` + token 预算 + 成本监控（面板显示钱） | ✅ 已解决 |
| 队列积压 | 并发上限 + 积压监控 + 优先级 | ✅ 已解决 |

### 1.5 排障类（出事了能否快速定位）

| 常见问题 | 我们的防线 | 状态 |
|---|---|---|
| "报告不准"怎么查 | run_id 三对一归因（数据错/工具没调/分析错） | ✅ 解决得很漂亮 |
| "Agent 突然变慢" | 监控面板趋势图 + 慢查询定位 | ✅ 已解决 |
| 日志大海捞针 | run_id 贯穿 agent_runs/tool_calls/sql_logs 三件套 | ✅ 已解决 |

## 2. 真实缺口（诚实版，按优先级）

| # | 缺口 | 影响 | 建议补法 | 工作量 |
|---|---|---|---|---|
| 1 | ~~**任务超时回收**~~ | ~~Worker 崩溃/断电后任务永远卡在 `running`~~ | **✅ 已实现（2026-08）：`recover_stale_tasks()` 回收超时 running 任务重置回队；调度器每 5 分钟执行 + Worker 启动自愈** | 已完成 |

## 3. 设计亮点总结（面试/汇报可重点讲）

**解决得最漂亮的三件事：**

1. **安全纵深**——"LLM 不可信"贯穿设计：工具白名单 → 参数强校验 → `agent_ro` 只读账号兜底。即使 LLM 被提示注入诱导，破坏上限也只是"一次只读查询"。这是很多 AI 项目缺失的一环。
2. **幂等体系**——检测幂等、任务 `idempotency_key`、诊断懒加载三层幂等。真实业务里"重复执行"是常态（调度重跑、用户重试），这套体系让系统怎么重跑都不出重复数据。
3. **可追溯**——run_id 贯穿 agent_runs / tool_calls / sql_logs 三件套，配合"数据错/工具没调/分析错"三对一归因，排障从"大海捞针"变成"按图索骥"。

**值得称道的工程取舍：**

- 规则引擎不用 LLM（可复现、可解释、零成本），Agent 只做调查取证
- 指标注册表唯一来源，换数据源只改口径配置、不动代码
- 宽表预聚合 + 只读账号，把"查询毫秒级"和"安全"同时做到
- 测试全离线（SQLite + MockLLM），CI 不依赖外部服务

## 4. 上线建议（结合缺口）

| 阶段 | 建议动作 |
|---|---|
| 立即（小成本） | 补任务超时回收（缺口 1） |
| 求职展示前 | 备份恢复演练一次（缺口 4），能讲"我验证过备份可用" |
| 真跑业务 | Worker 自愈（缺口 2）+ 报告质检（缺口 3）+ 阶段二（多进程/HTTPS/云数据库） |
| 规模化 | Redis 队列 + 多 Worker、ClickHouse、Prometheus 监控（README 已有路线） |
